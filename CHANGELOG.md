# Changelog

Every version of the `magos` package (the `version` in `plugin.json`, `.claude-plugin/plugin.json`, `plugin.yaml`, `SKILL.md` and the lane guard's `GUARD_VERSION`). A release is tagged `v<version>` on its release commit. The tag `v1.0` marks the skill release 3.4.0 from before the package became a plugin and was renumbered; it is not a plugin version. Install, pin, upgrade and roll back as `references/installation.md` describes.

## 1.0.2

Tag `v1.0.2`. A security release of the lane guard (`scripts/magos_guard.py`, `hooks/run-guard.cmd`, `hooks/hooks.json`). Every 1.0.0 and 1.0.1 install should upgrade, including the guard copies under `~/.magos/guard` that the Codex and Hermes hooks run.

### Security

- **Repository redirects.** A creation redirected into another repository with `git --git-dir`, `GIT_DIR` or `GIT_COMMON_DIR` (prefix, `env`, `export`, PowerShell `$env:`, cmd `set`) was allowed without a manifest: the hook judged the session's repository, or none when the session was outside any repository, so a claim there or a session repository with no other lane let an unplanned lane be created in the other repository. Each creation is judged in the repository it acts on, with that repository's mode, engagement and claims; under `GIT_COMMON_DIR`, which makes Git use two repositories at once, it is judged in both; a redirect the hook cannot resolve is denied in every mode, and so is a creation after a `GIT_DIR` or `GIT_COMMON_DIR` change the hook does not follow (`read`, `printf -v`, `+=`, `builtin export`, `Set-Content Env:`). `--work-tree` and `GIT_WORK_TREE` alone leave the judged repository unchanged.
- **Directory changes the shell may not make.** A `cd`, `pushd`, `Set-Location` or `GIT_DIR` change that the shell might never make before the creation moved the hook's judgement into another repository: one after `&&` or `||` followed by `;` (`false && cd other; git branch x`), inside `if`, `case` or a loop, in a function body or a PowerShell script block, in a background job (`&`), in a subshell `( )`, a command substitution `$( )`, a pipeline, `eval`, `source`, a PowerShell `( )`, or written as `env cd` (which changes nothing). The creation is judged in every directory the shell may be in, and the stricter verdict applies; in bash a subshell's change is known not to reach the commands after it. `cd dir && git switch -c x` and `cd dir; git switch -c x` are still judged in `dir` only.
- **Directories handed to wrappers.** `env -C <dir>` (`--chdir`) and `sudo -D <dir>` (`--chdir`) run git in `<dir>`, but the hook judged the directory the shell was in. They are judged like `git -C <dir>`. A session directory written with `~` (`~/repo`, `~user/repo`) is expanded, and a relative tool directory is joined to the payload's directory.
- **`cd` to a missing directory.** `cd` or `Set-Location` to a directory that does not exist, followed by `;` or a newline, let the following branch or worktree creation through, although the shell runs it in the prior directory. For `cd`, `pushd`, `chdir`, `Set-Location` and `sl`, the creation is judged in that prior directory and denied as unparseable when it is guarded, on every platform; the same holds for a `cd` the shell refuses (`cd /d dir` in bash, `cd dir extra`), while cmd's `cd /d dir` is followed into `dir`.
- **Shells and wrappers that hid a creation.** Text piped into a shell was read only when the shell stood right after the pipe, so `| FOO=1 sh`, `| env bash`, `| sudo -E sh`, `| command sh` and `| doas sh` let a creation through; `doas git branch x`, PowerShell `$out = git switch -c x`, `(git switch -c x)` and `@(git switch -c x)`, `env -S 'git switch -c x'`, and the commands `git rebase --exec` and `git bisect run` run were not recognised. All of these are read as the creation they run.
- **Escaped words.** In text a POSIX shell runs, a backslash escape hid a creation or a user-only command (`git swi\tch -c feat\ure`, `g\it`, `bash -\c`), and a cmd caret (`feat^ure`) did the same in cmd text. Words are read the way the shell that runs them reads them; in a shell the hook cannot name, a backslash in a git subcommand or branch name makes the creation dynamic. A bash backslash-newline joins the words around it (`main\<newline>2` is `main2`), and a `#` comment ends at the line's end, so a quote in a comment (`# Let's ...`) hides none of the following commands.
- **Git command spellings.** A branch name attached to its option (`git switch -cNAME`, `git checkout -qbNAME`, `git worktree add -bNAME <dir>`, `--orphan=NAME`), a global option whose value hid the subcommand (`--attr-source <v>`, `--config-env`, `--namespace`, `--exec-path`), a rename or copy written with bundled or abbreviated options (`git branch -mf`, `-qm`, `--mo`, `--cop`), the creating options of `git switch` and `git checkout` abbreviated to two letters (`--cr`, `--or`), a branch name after `git branch --sort <key>` or `--format <format>`, a push or fetch whose option value stood before the repository (`git push --exec <v> . HEAD:refs/heads/x`, `-o <v>`), a refspec that creates branches by a glob (`refs/heads/x-*`), a `git push` into a local repository (`git push . HEAD:refs/heads/x`, `git push ../other HEAD:x`), and an alias on a line that also held a recognised command created a branch without a manifest. Each is recognised; a push into a local repository is judged in that repository.
- **Unhooked shell tools in Claude Code.** The `Monitor` tool and MCP tools that run commands (`run_in_terminal`, `terminal`, `shell`, `exec_command`, `execute_command`, `start_process`, and names holding `command`, `exec`, `execute`, `process`, `bash`, `powershell` or `cmd`) were not inspected. They are hooked, the Claude matcher is generated from the guard's tool list, and the `command` string of every hooked tool and every MCP tool is read as a command line in addition to the judgement the tool's name calls for. `tool_input.cwd` is read as the session directory.
- **Payloads the hook could not decode.** A payload whose decoding raised (deep nesting gives `RecursionError` or `MemoryError`) was allowed. It is denied when its bytes hold a lane word (`git`, `worktree`, `isolation`, `EnterWorktree`, `magos` and the like), and an internal error on a call recognised as a lane creation or a protected command denies that call.
- **Programs in the working directory (Windows).** The launcher and the guard could run a `py`, `python` or `git` placed in the hook's working directory. Both set `NoDefaultCurrentDirectoryInExePath=1` before starting any program, and the launcher's cmd half finds its interpreter on PATH only.
- **User-only commands.** `override`, `arm`, `disarm` and `install` passed the host hook when a global option was written as `--repo=.`, `--lang=en` or abbreviated (`--rep .`), when `--` stood before the subcommand, when they were run through the launcher `run-guard.cmd`, and when a wrapper started them in a new console (`start`, `cmd /c start`, `Start-Process`). They are recognised in all of these forms, options are never abbreviated, the launcher runs only the `hook` subcommand (exit 2 for any other), and `install` needs a real console like `arm` (exit 17).
- **AUTO engagement.** When the check for other lanes failed (for example on the time budget), an auto-named worktree (agent isolation, `gh pr checkout`) was allowed, and more than 120 unmerged local branches made AUTO allow branch-only and auto-named creations without a warning. A snapshot that hides lanes counts as another lane; when the check fails, an auto-named creation is denied if an open claim, another local branch or a second worktree exists, a branch-only creation is judged when the repository holds a claim, and every undecided call writes a warning on stderr.
- **Overrides.** The host hook honoured an override record without consuming it. Only `plan` reads override records; after the user's override, a re-plan registers it in the claim, and the hook honours only the claim.
- **Claim store.** `release` with another spelling of the branch (`./x`, a different case) skipped the refusal for unmerged work and could delete a file outside the claim store; branch names that alias on Windows (`foo./bar` and `foo/bar`, names ending in `.claim`) overwrote another lane's claim; a newline in `--worktree` or `user.name` added lines to a claim file; two planners could register clashing names at once; and on Linux `release` with a spelling that holds `..`, `.`, an empty segment or a backslash (`zz/../FEAT`) found no claim. `release` reads the branch as a ref spelling (a backslash as `/`, empty and `.` segments dropped, `..` resolved), resolves the stored claim and deletes only its file inside the store; aliasing names are refused (exit 12); control characters are refused or replaced and claim keys are whitelisted; the name check runs again under the claim lock.
- **Tamper filter.** Writes aimed at the claim store, the guard home or the Hermes plugin directory by their absolute path are denied in armed or claimed repositories, as `.git/...` spellings are; `unlink`, `truncate`, `shred`, `ln`, `rmdir`, `rd`, `mklink`, `find -delete`, `Rename-Item`, `Move-Item`, cmd's `move` and `copy`, PowerShell's `cpi`, `sc`, `ac`, `ni` and `clc` and their aliases count as writers, also inside the text of a child shell (`cmd /c`, `bash -c`, `pwsh -Command`); a word escaped with a backslash, a backtick or a caret matches like its plain spelling. A copy is tested on every destination spelling (`-Destination:<path>`, operands before an option value such as `-ErrorAction Stop`); copying from the guard home is allowed.
- **Launcher on Windows.** An interpreter that is a `.bat` or `.cmd` shim did not return to the launcher, so its exit code was lost; a guard home whose path held `&`, `(`, `)`, `^`, `%`, `;`, `,` or `=` broke the generated entries or ran text from the path as a command; a guard home with an apostrophe broke the Codex entry. The launcher runs its interpreter through `call`, `install` refuses such a guard home on Windows (exit 2) and quotes the launcher path for each shell, and the launcher passes the guard's stderr to the host.
- **Chained git hooks.** `arm` keeps a repository's own `reference-transaction` hook as `reference-transaction.magos-prev` and runs it from the backstop. On POSIX a previous hook without the executable bit, which git itself never runs, failed with exit 126 in the `prepared` phase and so aborted every ref update in the armed repository. The backstop runs the previous hook only when it is executable, as git does.
- **Write adapters in Claude Code.** `git-integrate`, `git-cleanup`, `git-converge` and `git-sweep` set `disable-model-invocation: true`: only the user's slash command runs them.

### Added

- `version [--json]`: the running guard's version, the sha256 of its file, its path and the Python version. Read-only; agents may run it.
- `install` is version-aware and atomic: it prints `guard copy <old> -> <new>` or `guard copy unchanged (<version>)`, writes both files to temporary files and replaces both or neither (the launcher stays executable on POSIX), rewrites `guard/VERSION.json` (version, sha256, source, time) and appends to `<guard home>/audit.log` on every run that is not a dry run, and refuses to replace a newer copy with exit 18 (`DOWNGRADE_REFUSED`) unless `--allow-downgrade` is given.
- `doctor [--home DIR]` prints the running guard's version, compares the guard copy (under `--home`, `MAGOS_HOME` or `~/.magos`; from the copy itself, against the source its `VERSION.json` names) with it and prints the exact `install --host <host>` refresh command (also outside a repository), prints the copy's provenance from `VERSION.json`, checks the launcher of the generated Hermes entry, reports a Git older than 2.36, runs its self-test on a Git budget of its own and counts only the backstop's veto line as a pass, and reports a recorded backstop command whose script no longer exists or is older than the running guard, with the `arm` command to re-run.
- `arm` records, as the guard command of the backstop's deny message, the copy under `~/.magos` (or `MAGOS_HOME`) when that copy runs the same version, so a plugin upgrade does not leave the message pointing at a removed version; it records the previous `gc.packRefs` and `maintenance.pack-refs.enabled` values in `arm-config.json`, and `disarm` restores them. `arm` and `disarm` append to the repository's audit log.
- Claim format gate: every claim carries `v=` (any integer spelling, `v=01` included, reads as that integer); a claim written by a newer MAGOS is never misread (creations are denied with `CLAIM_NEWER_FORMAT` and a message that says to upgrade the guard, `release` refuses it, `plan` never overwrites it), and `list` shows unreadable and newer-format claim files.
- The Hermes entry that `install --host hermes` writes runs the Hermes plugin's own launcher, which follows the Hermes plugin's updates, when the plugin's guard is the installing guard's version and (on Windows) its path holds none of the characters above; otherwise it runs the guard copy, and `install` says why. The entry is valid YAML on every platform.
- With `--json`, a Git failure or an internal error prints a deny object on stdout; a Git call that fails without a message names its exit code.
- `scripts/sync_hosts.py` recognises a MAGOS plugin installed from a Claude Code marketplace and leaves the Claude command copies out of a default run, as it does for a clone in `~/.claude/skills`.
- A CI workflow runs the guard suite, the package contract suite and both source-contract runners (`--check`) on Windows and Linux with Python 3.9 and 3.14, runs the coverage commands of `.quality/qguard.json` on Windows with Python 3.14 and fails when a source file or the project has 90 percent line coverage or less, and checks that a release tag names the package version. CodeQL analyses the Python sources and the workflows.
- A security workflow (`.github/workflows/security.yml`) runs on pushes and pull requests to `main`, `develop_claude` and `develop_codex`, on `v*` tags, and weekly. On Windows and Linux with Python 3.14 it replays the confirmed findings of the 1.0.2 audit against the hook entry (`tests/codex/guard/data/security_regressions.jsonl`, 33 cases, each with the verdict and, for a deny, the reason it must get), runs the hardening and review suites, and checks the supply chain: every workflow pins its actions by commit SHA, gives every job read-only permissions (CodeQL's upload of its results is the one write), reads no secret, sets only listed environment variables (no `PIP_*` option but the version check), uses only listed actions with listed inputs and no container, service or reusable workflow, puts no expression into a script, and runs only listed command lines in bash, so nothing is fetched or installed but by hash-pinned, wheels-only pip; no tracked file holds a credential; the guard, the launcher and `sync_hosts.py` import no network module, the guard starts no program but git, and the git-layer hook runs only `git rev-parse` and the chained hook. In a partial clone, git itself fetches objects missing from the local store from the promisor remote when the guard reads a diff. zizmor audits the workflows and the Dependabot configuration with its pedantic persona and its online audits of the pinned actions, with inline ignores and configuration files disabled and every input collected, and fails on any finding or any file it cannot parse.
- Every CI install takes wheels only from a requirement file that pins each package by version and sha256: `.github/requirements` for Python 3.14 (pytest and PyYAML, coverage, zizmor) and `.github/requirements-py39` for the Python 3.9 legs, frozen at the last releases that support 3.9. Dependabot moves the SHA-pinned actions and the `.github/requirements` packages to new releases once a release is at least seven days old.

### Changed

- The guard's git runner starts only the local subcommands the guard uses (`--version`, `branch`, `check-ref-format`, `config`, `diff`, `for-each-ref`, `merge-base`, `rev-parse`, `status`, `worktree`) and refuses any other first argument with `GIT_FAILED` before git starts; none of these subcommands talks to a remote (in a partial clone, git itself fetches the objects a diff needs from the promisor remote).
- The deny for an auto-named worktree tells the agent to plan `worktree-<name>` and then call `EnterWorktree name=<name>`; a refused `release` names uncommitted changes in the lane's worktree as the reason.
- The launcher's failure warning names the absolute guard path and a stop instruction for every host; its POSIX part reads the payload once, starts Python once, and gives a Windows Python the Windows spelling of the guard path.
- The test line that made the Hermes plugin scanner refuse `hermes plugins update magos` for 1.0.1 (text echoed into a shell) moved into a data file the scanner does not read, and a contract test keeps that shape out of every shipped file. When the scan still asks for confirmation, an unpinned install updates with `hermes plugins install UlyssesLeoLee/MAGOS --force --enable`.
- The Claude Code plugin description no longer tells marketplace users to clone the repository as well.
- The skill's `compatibility` line states Git 2.36+ for the lane guard beside Git 2.30+ for the commands.

### Upgrade

1. Upgrade the plugin on each host (`references/installation.md`, "升级"). Restart every running Claude Code session: a session started before the update keeps running the previous guard. A Hermes install pinned with `--ref` moves its pin with `hermes plugins install UlyssesLeoLee/MAGOS --ref <40-character SHA of v1.0.2> --force --enable`; `hermes plugins update` and a reinstall without `--ref` keep the old commit.
2. Refresh the guard copy: run `doctor` from the new version (with `--home <dir>` for a copy installed with `install --home <dir>`) and, in your own terminal, the `install --host <host>` commands it prints. Compare each printed snippet with the entry in your host configuration and replace the entry when they differ: the Claude entry of a user-level snippet differs from 1.0.1 in every case (its matcher and its quoting); the Hermes command differs when the Hermes plugin is installed and, on macOS and Linux, in every case (1.0.1 generated invalid YAML there); the Codex command differs when the guard home's path holds an apostrophe.
3. In armed repositories, run `doctor` and re-run `arm`: the git-layer hook changed, so `doctor` reports the installed hook as different from this version until `arm` runs again, and it also reports a recorded guard command that is missing or older than this guard. A repository armed by 1.0.0 or 1.0.1 has no record of its previous pack-refs settings, so `disarm` leaves `gc.packRefs` and `maintenance.pack-refs.enabled` at `false`; restore Git's defaults with `git config --local --unset gc.packRefs` and `git config --local --unset maintenance.pack-refs.enabled`.
4. Scripts that abbreviate guard options (`--rep`) must spell them out, and scripts that run user-only commands through `run-guard.cmd` must run the guard script itself.

Compatibility: claim files of 1.0.0 and 1.0.1 are read unchanged. Exit code 18 is new.

### Known issues

- Every host receives the whole repository, `tests/`, `.quality/` and `.github/` included (more than 1 MB that the skills and hooks never run), because the marketplace source is the repository root. The Hermes plugin scanner reads these files as well; its verdict for 1.0.2 is safe, and contract tests keep the shapes it rates high out of every shipped file. A slim runtime payload is not part of 1.0.2.
- Nothing checks that a change to shipped files raises the version, and Claude Code updates an installed plugin only when the version changes.
- When the Hermes plugin holds another guard version, `install --host hermes` names `hermes plugins update magos` and the unpinned `--force` reinstall; a pinned Hermes install moves its pin instead (step 1 above).
- The source-contract runners keep tracked evidence for 8 of the 23 Codex cases and 5 of the 20 Claude cases; a run without `--check` writes the evidence of the other cases as untracked files.
- `references/lane-split.md` section 12 lists the limits of the lane guard itself.

## 1.0.1

Tag `v1.0.1` (commit `bab8606`).

### Security

- On Windows with Python 3.13 or later, a `cd` to a POSIX-rooted directory that cannot be mapped to a drive (`/does/not/exist`) before `git worktree add -b` or `git switch -c` was judged against a repository that does not exist, and the creation was allowed without a manifest. Python 3.13 changed `os.path.isabs` on Windows, and the hooks run under the `python3` found on the machine. The guard maps such a path to no directory and judges the creation in the session's repository.

### Fixed

- The package contract suite runs again (`tests/codex/contracts/skill_frontmatter.py` restored).

### Upgrade

Upgrade the plugin, restart every Claude Code session, and re-run `install --host codex|hermes` for the guard copy under `~/.magos/guard`.

## 1.0.0

Commit `74bf82f`; no tag. Do not install or pin it: its guard has the Windows Python 3.13+ bypass fixed in 1.0.1.

- The package is renumbered from 3.4.0 to 1.0.0 and installs as the plugin `magos` from the Claude Code, Codex and Hermes plugin marketplaces (`.claude-plugin/`, the root `plugin.json`, `plugin.yaml` and `__init__.py`), with the entry skill `skills/git-orchestrator`; Claude Code also loads a clone in `~/.claude/skills/magos` as the plugin.
- `/GitSweep`: `/GitConverge`, then the lease-guarded deletion of merged remote branches.
- The lane guard: a branch or worktree needs a registered file manifest before it is created, and a creation that overlaps another lane is denied (Claude Code plugin hooks, generated Codex and Hermes entries, and the opt-in `reference-transaction` backstop).
