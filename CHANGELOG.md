# Changelog

Every version of the `magos` package (the `version` in `plugin.json`, `.claude-plugin/plugin.json`, `plugin.yaml`, `SKILL.md` and the lane guard's `GUARD_VERSION`). A release is tagged `v<version>` on its release commit. The tag `v1.0` marks the skill release 3.4.0 from before the package became a plugin and was renumbered; it is not a plugin version. Install, pin, upgrade and roll back as `references/installation.md` describes.

## 1.0.4

Tag `v1.0.4`. A feature release: the new command `/GitPlan`, which plans, before any sub-agent starts, how one task is divided into lanes that own different files and are merged back as one whole, lists the requirements, the lanes and their outcomes in tables, and later converges the lanes and supplements that list with what each lane changed, backed by four new subcommands of the lane guard (`scripts/magos_guard.py`). Every install should upgrade, and the guard copies under `~/.magos/guard` that the Codex and Hermes hooks run must be refreshed: a guard of 1.0.3 has no set subcommand, and `/GitPlan` stops at its version check.

### Added

- **`/GitPlan`.** The eighth command (`/GitPlan` in Claude Code, `/git-plan` in Hermes, `$git-plan` in Codex), with the adapters `commands/GitPlan.md` and `skills/git-plan/` (`SKILL.md`, `agents/openai.yaml`) and the contract `references/commands.md` section 8. Forms: `/GitPlan <set> --into <branch>` (preview), `--into <branch> --apply [--create]`, `<set> --status`, `<set> --amend --expect-revision <n> [--apply [--create]]`, `<set> --converge [--include-active]`, `<set> --converge --apply [--include-active] [--land] [--expect-revision <n>]` and `<set> --release`. The set name is `[a-z0-9][a-z0-9-]{0,23}`, and `--into` is a local branch that is not `main`. A preview investigates Git (branches, worktrees, open claims, the target tip, remote freshness as the local records show it) and the code (layout, entry points, the repository's build, test and lint commands, shared files, hot spots, imports across boundaries), writes the requirements of the task, divides it into at most 12 lanes with exclusive file ownership that are named after the topic of their change, proves the division with `magos_guard.py set-plan --dry-run` and ends with a readiness verdict (`READY` or `BLOCKED`), the next command and the remedy of every failed gate; it fetches nothing, registers nothing, and its only write is a scratch spec file outside every worktree. `--apply` registers exactly the spec of the latest preview of the same set and target, byte for byte, and makes a new preview and stops when there is none, when the user asked for a change since, when its `base` differs from the live target tip, or, for an amendment, when it was built from another record revision than the current one; `--create` also creates the registered lane branches and worktrees from the recorded `base`, and without it the report prints the `git worktree add` lines.
- **Requirements, lanes and outcomes in tables.** The plan states the requirements of the task (1 to 12, each an id such as `R1` and one sentence), and every lane serves 1 to 12 of them and states the outcome it delivers (`serves`, `outcome`). Every report that shows the plan prints two tables, rendered from the data the guard proved (a preview) or stores (afterwards) and never from memory: the Requirements table (`Req`, `Requirement`, `Lane(s)`, `Planned outcome`, one row per requirement) and the Lanes table (`Lane`, `Branch`, `Worktree`, `Owns`, `Needs`, `Acceptance`, one row per lane; `--status` and `--converge` add `State` and `Head`), then the merge line, the owner lane of every shared file (lockfiles, generated files, registries, migration numbers, version files, changelogs) and at most five risks. The stored sheet holds them in at most 8192 characters. `--status` and `--converge` print the tables again from the record, with `[x]` for the lanes that are `ready` or `integrated` and their recorded heads, followed by **Remaining TODO**: the lanes still to finish, the merges, the repository checks, the post-merge tasks, the land and the release. The tables are both the plan the user reviews and the TODO reference for the merge. A requirement that no lane serves, a lane that serves none, and a requirement id that is unknown, repeated or missing in `serves` are refused with exit 24 (`UNSERVED`, `UNKNOWN_REQUIREMENT`, `DUPLICATE`, `RANGE`, `MISSING`), naming the field.
- **Names show the topic of the change.** A lane id is a topic slug (`[a-z0-9][a-z0-9-]{0,23}`, one to three words such as `claim-store`, `sweep-readiness`, `launcher-exit-codes`), the lane branch is exactly `agent/<set>/<id>` and the name of the lane worktree directory ends with `-<set>-<id>` (by default `<parent of the main worktree>/<repository directory name>-<set>-<id>`), so `git branch` and `git worktree list` read as a list of topics. The guard refuses an ordinal or generic id (only digits, one letter, `l1`, `lane-2`, `task3`, `worker-1` and the like, and the reserved `integration`: `GENERIC_ID`, `RESERVED`, `FORMAT`, `DUPLICATE`) and a branch or worktree name of another form (`BRANCH_FORM`, `WORKTREE_FORM`, `WORKTREE`) with exit 24, and the message names the compliant name. The integration branch stays `agent/<set>/integration`; the set name and the requirement ids are not subject to the ordinal rule.
- **The changes summary and the supplemented list.** When a lane is recorded `integrated`, the guard computes from git a summary of what the lane changed, against the local target branch of that moment, and stores it in the lane record as `changes` (`commits`, `subjects` (at most 8, oldest first), `more`, `files`, `insertions`, `deletions`, `paths` (at most 12) and `paths_more`); it is null before, a repeated `integrated` update keeps it, and `set-show --json` carries it per lane. After the merge the original list is supplemented, not replaced: the converge apply report, `--status` and `--release` print the same two tables with every row and column kept, a `Changes` column on the Lanes table (`<commits> commits, <files> files, +<insertions>/-<deletions>`), a `Result` column on the Requirements table (the first commit subject of each integrated lane that serves the requirement, and `pending: <lane>` for the others), the **Changes summary** (one line per lane with its commit subjects and paths) and a `Total` line, followed by **Remaining TODO**.
- **Optimistic lock.** Nobody holds a lock while the lanes work. The record carries a `revision` that every change compares and increments and the target tip the plan was made against (`base`), and a lane records the head it was marked `ready` at. A stale plan is detected and refused, never overwritten: `--amend` and, optionally, `--converge --apply` take `--expect-revision <n>`, a target that moved so that the files changed by its commits outside the set's own work (what the integration branch and the recorded lane heads hold) intersect a lane manifest makes the finding `STALE_PLAN`, and an amendment moves `base` to the live target tip.
- **Convergence.** `--converge` previews, and `--converge --apply` merges, the `READY` lanes in dependency order into one integration branch `agent/<set>/integration` (created with a plain `git switch -c` from the current target tip in the invoking worktree): each recorded head is merged with `git merge --no-ff` and recorded `integrated` with `set-update`, and the repository's checks run on the result. A conflict runs `git merge --abort` and stops the run, never resolved with ours, theirs or by hand; the completed merges stay on the integration branch only, and the report names the lane, the files, the error text and the integration start SHA. `--include-active` takes an `active` lane that holds changes of its own against the current target as `ready` at its current tip, which the preview shows as its Head; in an apply that is the user's acceptance of that tip, and a tip that moved since the preview stops the apply with a new preview. `--land` adds one `git merge --ff-only` of the integration branch into `<branch>`, only while `<branch>` still sits where the integration branch was cut from (otherwise `LAND_REFUSED`). `--release` prints the final checklist, then removes the claims and the record; no branch, worktree or integration branch is touched. The command never pushes, never deletes a branch or a worktree, never touches `main`, never uses `override`, and merges nothing but a recorded lane head into the integration branch.
- **Lane findings and remedies.** The preview of a convergence evaluates every lane: `INTEGRATED`, `READY`, the pending `BLOCKED`, `NOT_READY` and `WAITING` (the lane sits this run out), the failing `MISSING_BRANCH`, `DIRTY`, `IN_PROGRESS`, `NO_MERGE_BASE`, `OUT_OF_LANE`, `SHARED_CHANGE`, `MOVED`, `CLAIM_DRIFT` and `STALE_PLAN` (the whole command stops, so a ready lane that is inconsistent is never merged around) and the hint `PREDICTED_CONFLICT`. The readiness is `READY`, `PARTIAL` or `BLOCKED`. Every failed gate, failing finding, guard exit code and stop of an apply is followed by the action that lifts it (`references/commands.md` section 8, **Remedies**), which the command never performs.
- **Guard subcommands.** `set-plan --set <name> --target <branch> --spec <file>|- [--dry-run] [--amend --expect-revision <n>]` validates the spec (1 to 12 requirements each served by a lane, at most 12 lanes with topic-slug ids that each serve existing requirements and state an outcome, 200 manifest entries per lane, branches exactly `agent/<set>/<id>` and distinct worktree paths whose directory names end with `-<set>-<id>`, pairwise disjoint manifests by exact glob intersection, `depends_on` ids that form a DAG, every shared file inside its owner's manifest, `base` equal to the live target tip, each lane judged against the other claimants) and then writes every lane claim, the claim of the integration branch and the record in one atomic operation, or nothing; `set-show --set <name> [--drift]` reads the record and the view of every lane (the requirements with the lanes that serve them, branch, tip, commits ahead of `base`, worktree state, the stored `changes`, files outside the manifest, files changed by two lanes, target moved, merge order); `set-update --set <name> --expect-revision <n> --lane <id> --state active|ready|integrated|blocked [--head <sha>] [--note <text>] [--integration <branch>]` records the progress of a lane (`ready` needs `--head` equal to the branch tip and every changed file inside the manifest, `integrated` needs the recorded head to be in the target or the integration branch and stores the `changes` summary of the lane); `set-release --set <name> [--reason <r>] [--abandon]` removes the claims and the record once every lane is integrated. None of them is user-only: they run through the host hook like `plan`, `release` and `list`, options are never abbreviated, and with `--json` every outcome is one object with `decision`, `code`, `message` and `exit_code`.
- **The set record.** `<git-common-dir>/magos/sets/<set>.json`, written only by the guard (the tamper filter denies agent writes under the store): the `revision`, the target, the `base`, the title, the requirements, the sheet, the notes, the shared files, the integration branch once the first lane is integrated, and per lane its branch, worktree, manifest, dependencies, the requirements it serves, its outcome, acceptance, state, head, the commit its last `ready` was measured against (`ready_target`), note and `changes`. A record of a greater format version is never misread or overwritten: every set command that names it refuses with exit 23.
- **The integration claim.** `set-plan` registers a claim for `agent/<set>/integration` (the single marker entry `.magos/integration/<set>/`, the extra keys `set=<name>` and `role=integration`), which is why a plain `git switch -c agent/<set>/integration <target tip>` is allowed in a guarded repository. The claim holds no files and is exempt from overlap judgement in both directions: it restricts no lane's manifest and is never a claimant, and the creation of that branch is judged for its name and the existence of the claim only.
- **Exit codes 19 to 24.** `19` `STALE` (the `kind` of a denial is `base` or `revision`, with `expected` and `current`), `20` `SET_EXISTS`, `21` `SET_UNKNOWN`, `22` `OUT_OF_LANE`, `23` `SET_NEWER_FORMAT` and `24` `INVALID_SPEC` (a spec or option value that is invalid in itself; the message names the field). The codes `10`, `11`, `13`, `14`, `15` and `16` keep their meaning, `12` also reports a branch name or worktree path that clashes with the repository, and a failure that the repository or the record causes keeps its existing code.
- **`list` and `doctor`.** `list` shows the `set` and the `lane` (or `role`) of a claim. When `sets/` holds a file or a claim carries `set=`, `doctor` prints `sets: <n>, unreadable: <n>, newer-format: <n>` and a line for each problem: a lane claim that is missing or differs from the record, an `active` or `ready` lane whose branch vanished, a set whose target branch is gone, claims of a set without a record (an interrupted registration), and an unreadable or newer-format record. A repository without sets prints what 1.0.3 printed, the version aside.
- **Documentation.** The three READMEs describe `/GitPlan`, the eight commands, the command names per host and the install steps; `references/pressure-tests.md` has the **GitPlan pressure tests (v1.0.4)**, among them ordinal lane ids, a requirement that nobody serves, a branch or worktree that does not carry the topic and the supplemented list after the merge; the source-contract cases `git-plan/forms-and-help`, `git-plan/exclusive-lanes-and-optimistic-lock`, `git-plan/converge-and-hard-stops` and `git-plan/package-wiring` pin the command.

### Changed

- **Plain `plan` and `release` refuse the claims of an open set.** While the record of a set exists, a plain `plan` that would write the claim of a branch of the set (a lane branch or the integration branch, also when that claim is missing or lacks its `set=` line: an amend, other entries, the re-plan after an override) is refused with exit 14 (`lane_in_set`) and `release` of any claim of the set with exit 16 (`blocked_set`): a set is changed only through `/GitPlan`, with `--amend` (which writes a missing or set-less claim of the set again) and `--release`; of a record the guard cannot read or that a newer MAGOS wrote only the integration branch `agent/<set>/integration` is known, so a lane counts only through the `set=` line of its claim.
- **`plan` keeps the registered worktree path.** A `plan` without `--worktree` (an amend, the re-plan after an override) keeps the worktree path the claim registers, which the host hooks enforce at the creation, and its success message prints the creation command with that path (`<path>` when the claim registers none).
- **Open lane claims of a set block cleanup.** The claim of a lane of a set is an open claim, active-owner evidence like any other, so `/GitCleanup`, `/GitConverge` and `/GitSweep` report its branch as `BLOCKED_ACTIVE_OWNER` while the set is open; `--release` lifts it.
- **Paths from the top of the work tree.** Every git call of the guard carries `-c diff.relative=false`, so a `diff.relative=true` configuration does not cut the files of a branch down to the directory the call starts in: the hook in a session whose directory lies below the top of the work tree, and `plan`, `check` and the set subcommands with a `--repo` below the top, read every committed path from the top of the work tree and judge it against the manifests.
- **Submodule pointers are evidence.** Every `diff`, `log` and `status` call of the guard carries `--ignore-submodules=none`, so neither `diff.ignoreSubmodules`, nor `submodule.<name>.ignore`, nor the `ignore` of `.gitmodules` hides a changed submodule pointer (a gitlink) or a submodule checkout that differs from it: `plan`, `check` and the hook count such a path as committed or uncommitted evidence and judge it against the manifests, plain `release` refuses a branch whose worktree holds such a change, the pinned `-c diff.ignoreSubmodules=none` carries the same into the `status` Git runs inside each submodule checkout, and the set subcommands count it among the files of a lane, the drift of the target, the changes summary and the test of a clean worktree.
- **Guard version.** `GUARD_VERSION` is 1.0.4, and `/GitPlan` checks `magos_guard.py version` first and stops below 1.0.4.
- **Eight commands.** Every text that enumerates the commands says eight: `SKILL.md`, `references/commands.md` (all eight commands accept `--help` and `--lang`), the plugin manifests, `COMMAND_NAMES` of `scripts/sync_hosts.py`, `INDEX_DESCRIPTIONS` of `__init__.py`, `references/installation.md` and the three READMEs. Five adapters write to a repository and set `disable-model-invocation: true` in Claude Code (`git-integrate`, `git-cleanup`, `git-converge`, `git-sweep` and `git-plan`); the Codex adapters all disable implicit invocation, and `git-plan` refuses to write on Hermes unless it is invoked explicitly.

### Known limits

- **Sets live in one clone.** The set record and the claims of its lanes are in the git directory of the clone that registered them. Fetch and push do not share them, so another clone of the same repository does not see the plan or its claims.
- **Topic names are checked for form, not for meaning.** The guard checks that a lane id is a topic slug and refuses the ordinal and generic ids, but it neither counts the words nor judges whether the name fits the change: naming the topic after the requirement and the owned paths is the duty of the executor.
- **Semantic coupling is not detected.** The guard proves that the file lists of the lanes are disjoint, not that the code of two lanes is independent. Files that import each other belong in one lane, which the partition rules of `/GitPlan` ask for and the guard cannot check.
- **A guard of 1.0.3 cannot see the set record.** It has no `set-*` subcommand (a usage error), does not show sets in `list` or `doctor`, reads the claims of a set as ordinary claims, judges the marker entry of the integration claim as the declared manifest of a lane and cannot refuse `release` or `plan --amend` of a claim of a set, or its re-plan after an override, so a set whose claims an older guard changed (an emptied worktree and a stored override fingerprint included) shows `mismatch` or `missing` in `set-show` and in `doctor`. Refresh the guard copy (Upgrade).
- **The limits of the lane guard** (the classes of command text the hooks do not read, listed under 1.0.3 and in `references/lane-split.md` section 12) are unchanged.

### Upgrade

1. Upgrade the plugin on each host (`references/installation.md`, "升级"). Restart every running Claude Code session: a session started before the update keeps running the previous guard. A Hermes install pinned with `--ref` moves its pin with `hermes plugins install UlyssesLeoLee/MAGOS --ref <40-character SHA of v1.0.4> --force --enable`; `hermes plugins update` and a reinstall without `--ref` keep the old commit.
2. Refresh the guard copy: run `doctor` from the new version (with `--home <dir>` for a copy installed with `install --home <dir>`) and, in your own terminal, the `install --host <host>` commands it prints. Compare each printed snippet with the entry in your host configuration and replace the entry when they differ.
3. Nothing else changes for scripts.

Compatibility: claim files of 1.0.0 to 1.0.3 are read unchanged. A claim of a set carries the extra keys `set=` and `lane=` (the integration claim `set=` and `role=integration`), which older guards ignore.

## 1.0.3

Tag `v1.0.3`. A hardening release of the lane guard (`scripts/magos_guard.py`, `hooks/run-guard.cmd`) and an improvement of `/GitSweep`. Every install of an earlier version should upgrade, including the guard copies under `~/.magos/guard` that the Codex and Hermes hooks run.

### Security

- **`git update-ref --stdin` records.** The instructions are read only from the sources of that invocation that the hook can see, as the words the shell hands over (quotes removed): a here-string, the here-documents of the line, and a directly piped `echo`, `printf`, `Write-Output`, `Write-Host` or a `cat` of here-documents. The record is dynamic, and denied as unparseable where creations are guarded, unless every `create` and `update` is a plainly read name: `\0`, `\n`, `\t` and `\r` separate the fields as printf writes them, and any other escape (`\x62`), a quote or an expansion in a name, a `printf` format, an empty name, a name git refuses and an unreadable source (a file, another command, a substitution, no input) make it dynamic. A command that only mentions `update-ref --stdin` is not read. A plain record creates its branch only with a manifest.
- **Escaped program words in a shell the hook cannot name.** In a tool whose shell is unknown (the Hermes `terminal` tool, `shell`, MCP command tools), a program word written with a backslash, a backtick or a caret (`g\it`, ``g`it``, `g^it`, also after `env`) is read as the program it spells without the escape; the creations and possible changes of that line are dynamic and denied as unparseable.
- **Abbreviated `git rebase --exec`.** `--ex` and `--exe`, with the value attached by `=` or separate, are read like `--exec`, and the commands they run are judged. `--e` is ambiguous for git and runs nothing.
- **`git --shallow-file`.** The global option takes a separate value, so the subcommand after it is read: `git --shallow-file <value> branch <name>` creates `<name>` and is judged.
- **Alias check.** The check for aliases reads the subcommand of every `git` word of a line after the values of the global options (`-C <dir>`, `-c <key=value>`, `--git-dir=<dir>`, a path-qualified `git`), in one pass, so a line of any length is read within the time budget.
- **`refs/heads` in any case.** `refs` and `heads` under it in any letter case (ASCII letters) are read as a branch on every platform (it is one on the case-insensitive file systems of Windows and macOS: `refs/HEADS/x`, `REFS/heads/x`). One pattern is shared by the host hook, which reads it in `git update-ref`, in `git push` and `git fetch` refspecs, in `update-ref --stdin` records and in `git symbolic-ref`, and by the `reference-transaction` hook of an armed repository, which vetoes a creation under such a spelling without a claim.
- **`git update-ref` options.** Options are read as git reads them: `-m <message>` and `-mMESSAGE` take a value, `--std` and `--s` are `--stdin`, and the bundled and separate forms of `-d`, `-z` and `-m` are read, so a creation written with them is judged. Deleting a ref and a `--no-deref` update of `HEAD` create nothing.
- **`Start-Process` working directory.** `Start-Process git` runs git in its `-WorkingDirectory` (also `-Wo`, `-wo` and the colon form `-WorkingDirectory:<dir>`), and a creation in its `-ArgumentList` (`-a`, colon forms) is judged in the repository of that directory; without `-WorkingDirectory` it is judged where the shell is.
- **PowerShell option spellings.** Every spelling of `-Command`, `-CommandWithArgs` and `-EncodedCommand` that `powershell` and `pwsh` accept (`-e`, `-ec`, `-EncodedC`, `-Co`, `-Comm`, `-cwa`) is read in the command walk, in the tamper filter and in a Codex argv, where the words after a PowerShell or cmd command option are joined into the text that runs. `-ex Bypass` is the execution policy option, and `bash -ec` is bash.
- **PowerShell backtick.** In PowerShell text the backtick is the escape character with its special sequences: ``g`it`` is `git`, ``git sw`itch`` is `git switch`, and ``gi`t`` is `gi` followed by a tab, which runs no git.
- **Word gate.** The gate that decides whether a line is read sees the line and its inner texts without escapes and quotes (`g''it`, `"g"it`), and a word that runs a script or a shell (`.`, `source`, `bash <script>`, `sh <script>`, also in a command substitution or a here-document fed to a shell) opens it, so the creation that a small script file makes is read and judged. A line with neither is not read.
- **Missing directories.** Records and inner-text states that differ only in the prior directory, or the followed chain, of a `cd` to a missing directory stay apart, so each creation is judged in the directory the shell is in at that point. A line whose later creation runs in another engaged repository is denied as unparseable.
- **Launcher.** In both halves the launcher passes on to the next interpreter when `py` exits 103 or 112 (`py` without a Python runtime), and the verdict of the guard that runs comes through with exit 0. Any other exit of `py` is a guard failure (`exit code <n>`, exit 2 with `--strict`) and starts no further interpreter.
- **Claims under a refused name.** A claim file stored under a name that the Windows alias rule refuses (for example a name ending in `.claim`, as 1.0.1 stored it) allows the creation of its branch. `plan --amend` for that name is refused with exit 12 and names the rule, `list` shows the claim with the rule (`refused_name` in `--json`), and `doctor` names it. A name without a claim is denied.
- **Redirections.** The redirections of the shell are words of their own and are skipped, with their target, before the program word (also after prefix assignments and wrappers), between a program and its subcommand and among the words of a git invocation, so `>/dev/null git switch -c x`, `git -C . >/dev/null switch -c x`, `git branch -m old new >/dev/null`, `git update-ref >/dev/null refs/heads/x HEAD` and `bash -c >/dev/null '..'` are judged like their plain forms; `2>&1`, `>&2`, `&>f` and `>|f` are one word. The word gate, the alias check and the tamper filter skip them too. A quoted or escaped word (`'>x'`) is no redirection.
- **`git branch` bundled short options.** The letters of a short-option word are read as git reads them, up to the first letter that takes a value: `-df`, `-dr`, `-rd` and `-vd` delete or list and create nothing, and `-mr`, `-m -r`, `-m -a` and `-c -r` rename or copy, so the new name is judged (`git branch -m -r a b` creates `b`).
- **`git symbolic-ref` and dynamic ref words.** `git symbolic-ref` reads `-m <reason>` (also `-qm`) and `--`, so `git symbolic-ref -m why HEAD refs/heads/z` creates `z`. A first positional word of `git update-ref` that is dynamic (`$ref`), and a dynamic name or target of `git symbolic-ref`, is a dynamic creation when it may name a branch (also behind `xargs`); only a literal `refs/` namespace other than `heads` names none.
- **Refspec destinations.** The destination of a fetch, pull or push refspec is read on its raw text: `refs/heads/refs/x` creates the branch `refs/x`, another destination that begins with `refs/` creates no branch, and a push refspec with an empty source (`:refs/heads/x`) deletes and creates nothing.
- **Names git accepts.** Whitespace and letters outside ASCII (U+00A0, U+2003, U+3000) belong to a branch name, and a leading dash is a name for `update-ref`, `symbolic-ref`, `fetch`, `pull` and `push`, whose operand is a full ref (`refs/heads/-x`); only a name that git certainly refuses is dropped.
- **Time bounds.** A chain of relative `-C` values and the nesting of groups and brace blocks (98,000 deep, in bash and in PowerShell) are walked in time linear in the length of the command, so a line of 200,000 characters is read within the time budget.

### Added

- **`/GitSweep --push`.** With `--apply`, after the local converge and before the remote deletions, one fast-forward push publishes `<branch>`: `git push --recurse-submodules=no --no-follow-tags <remote> refs/heads/<branch>:refs/heads/<branch>`, never forced and never `--no-verify`, so remote branches merged only into the local `<branch>` are deleted in the same run. The push is skipped (`PUSH_SKIPPED`, with the failed condition) when the live remote `<branch>` is not an ancestor of the local one, when `<branch>` is `main` or the remote default, when the converge phase stopped or its validation failed, or when the remote sweep is `UNKNOWN`. When the live remote tip equals the local tip nothing is pushed and the report says `PUBLISH_NOT_NEEDED`; otherwise the push runs even when no remote branch depends on it. A failing push is reported as `PUSH_FAILED` and never retried; a push after which the remote tip differs from the local tip is `PUSH_UNCONFIRMED` and counts as failed. A push never reaches a repository other than `<remote>` and never recurses into submodules: both push commands carry `--recurse-submodules=no`. The preview predicts the push from the local refs, with or without `--push`, and does not contact the network; it counts the commits that no `refs/remotes/<remote>/*` ref holds yet (`git rev-list <converged tips> --not --remotes=<remote>`), and phase 1 adds at most one merge commit per merged source. The report gives the remote tip before and after and the exact range and commit count; undoing a publish takes a force push, which the command never makes.
- **Readiness block.** The preview of `/GitSweep` ends with a verdict (`ONE_SHOT`, `PARTIAL` or `BLOCKED`), a recommended command (`/GitSweep <branch> --apply` with `--remote` and `--lang` as given, carrying exactly the flags that lift something: `--discard-ignored` with the ignored files it deletes listed, `--push`, whether or not it was typed, when a remote branch is `PUSH_THEN_DELETE`, and a typed `--push` whose publish prediction says the push will run, with the commits it publishes) and the remaining items with their evidence and remedies. The verdict judges the recommended command, not the command as typed: a preview computes everything that depends on `--discard-ignored` as if the recommended command had been typed, so the remote classification shows the state that command reaches, and an apply uses the flags it was given. The end state is only `main` and `<branch>` as local branches, the worktrees of the deleted branches removed, and every remote branch deleted or `NOT_TOUCHED`; a worktree the command never touches (a detached one, or one that holds `main` or another kept branch) is listed in the report. Apart from a typed `--push` that will run, a flag that lifts nothing is never recommended, and a flag that discards files or publishes commits is never added silently; a typed `--push` whose publish will not run is dropped from the line, and the report says why.
- **Remedies.** Every failed gate, delete blocker, `UNKNOWN` status and `PREDICTED_CONFLICT` in a `/GitConverge` or `/GitSweep` report is followed by the action that lifts it (`references/commands.md` section 6, **Remedies**; section 7 adds the remedies for remote findings, among them the one for a `--remote` that `git remote` does not list, and separate remedies for `PUSH_THEN_DELETE` without `--push` and for `PENDING_PUSH`). The command never performs these actions. A target that matches an existing branch only in letter case is answered with the exact existing name, never with a branch that differs only by case; a repository whose trunk has another name than `main` is told to create `main` deliberately or not to use the command.
- **Run state.** The `/GitSweep` apply report ends with `COMPLETE` or `PARTIAL`. A `PARTIAL` report lists the remaining items with their remedies and ends with two lines, in this order. A remedy changes the repository, and an apply whose plan is older than the repository stops with a new preview, so `Next preview:` is the same line without `--apply`, to run once the remedies are done so that the preview becomes the earlier plan, and `Next command:` is the line to run after that preview (when that preview recommends another line, run the recommended one). Both lines carry their flags in the order `--apply`, `--discard-ignored`, `--push`, `--remote`, `--lang`, with `--remote` and `--lang` as given. The `Next command:` line carries `--push` when some remote branch ended `PUSH_THEN_DELETE` or `PENDING_PUSH` for a reason that a rerun with `--push` can clear, or when `--push` was typed and the publish prediction says the push would still run; it never carries `--push` when the only reason is that `<branch>` is the remote default; with phase 2 `UNKNOWN` it carries `--push` only when it was typed. Both lines are left out when no rerun would change anything.
- **Documentation.** `README.ja.md`, a Japanese edition that follows the Chinese README section for section; all three READMEs share one language switcher and describe the 1.0.3 commands, the command names per host and the install steps.

### Changed

- **Remote classification against the converged target.** A remote branch is classified against the converged target (the local `<branch>` after the converge phase; in a preview, its tip together with the tips of the sources that will be merged), so a preview and the apply after it agree. `PUSH_THEN_DELETE` marks a branch whose deletion depends on the publish step, which is predicted to run (in a preview with or without `--push`; an apply without `--push` leaves it and reports "kept: `--push` not typed"); `PENDING_PUSH` marks a branch that no push of this run clears: the publish is not predicted to run (for example `<branch>` is the remote default), or the push was skipped, failed or unconfirmed. The remedy of the first is to rerun with `--push` or, once local `<branch>` holds its tip, to push `<branch>` by hand; the remedy of the second is to clear the condition the report names.
- **All gates at once.** `/GitConverge` and `/GitSweep` evaluate every gate and report every failed one together with its remedy. `/GitSweep` adds the gate `--remote <name>` not listed by `git remote`, with its remedy, and a failed gate makes its verdict `BLOCKED`. The `Default` line of the `/GitConverge` help says that every failed gate and blocker is followed by the action that lifts it.
- **Hard stops.** The `/GitSweep` hard stop on pushing commits and tags reads: except the one fast-forward push of `<branch>` that `--push` makes. The lease-guarded deletion of one named remote branch at a time is the other push. `/GitConverge` pushes nothing.
- **Option hints.** The one-line hints of `git-sweep` (the Hermes description and the Codex short description) list `[--apply] [--push] [--help]`; the full usage lists every option, `--remote` included.
- **Argument safety and names.** Every git command of `/GitConverge` and `/GitSweep` runs as an argument list, never as a shell string or a PowerShell expandable string, and each ref name, remote name, path and SHA is one argument; a command printed in a report quotes each of them in POSIX single quotes. The name of a source branch, or of a remote branch that is not `NOT_TOUCHED`, that holds a character outside ASCII letters, ASCII digits and `.` `_` `/` `+` `-`, or starts with `-` or `+`, is never passed to a command: a local source with such a name is `UNKNOWN` (neither merged nor deleted; the remedy is to rename it), and a remote branch with such a name is `BLOCKED_BAD_NAME`, which keeps the readiness verdict at `PARTIAL`. The typed `<branch>`, the remote default and `main` are covered by the argument rule alone.
- **One URL.** The remote sweep and the publish step are `UNKNOWN` unless `git remote get-url --all <remote>` and `git remote get-url --all --push <remote>` each print exactly one URL and the two are identical, because a push goes to every URL; the remedy is `git remote set-url --delete <remote> <extra-url>` for each extra URL, and `git config --unset-all remote.<remote>.pushurl` for a separate push URL.
- **Live remote `HEAD`.** Phase 2 is `UNKNOWN` unless the `ref:` line of `git ls-remote --symref` for `HEAD` names exactly the remote default; a live `HEAD` that is detached, unborn or missing makes the whole sweep `UNKNOWN`, and the remedy is to set the default branch on the remote or its host (`git remote set-head <remote> --auto` cannot fix it).
- **Worktrees with submodules.** `BLOCKED_SUBMODULE` is decided the way git decides: the git directory of the worktree contains a `modules` directory, or a submodule path of the worktree is populated; deinitializing does not lift it. The command cannot remove such a worktree; after confirming that it holds nothing unique, remove it yourself with `git worktree remove --force <path>`, or keep it. The branch stays as long as the worktree does.
- **Ignored-file overlap.** The preview runs the ignored-file overlap test of the apply for every source to merge and marks a hit `PREDICTED_IGNORED_OVERLAP`, with the source, the changed path and the ignored entry; it counts against `ONE_SHOT`, and the remedy is to move or delete the ignored entries that the report names.
- **Long-lived roles.** A remote branch has a long-lived role only with recorded or observed evidence: a policy file, CI trigger filters, matching release tags, or at least two merge commits between the branch and a survivor, counted in both directions on the `--first-parent` chains of the two recorded SHAs. One merge is a lane merge, merges inherited from before the branch was cut do not count, and a role inferred from the name alone does not count.
- **Plan and report.** An apply records the converge plan first and, after the converge phase and before the first remote write, every remote candidate with its SHA, classified against the actual `<branch>` tip. The preview and the inline help say that each remote deletion closes the open pull requests that use the branch as their head, and on some hosts closes or retargets those that use it as their base; the preview cannot see them. The local deletion never includes `main`.
- **`update-ref --stdin` from a file or another command.** An `update-ref --stdin` whose input is a file, another command or text with an expansion is denied as a dynamic creation even when it only deletes, because the hook cannot read it; it reads the instructions only from a here-document, a here-string or a piped `echo`, `printf`, `Write-Output` or `Write-Host`.
- **Long directory spellings.** A directory spelling longer than 4,096 characters is an unknown directory: a creation in the same invocation as a chain of `-C` values or `cd` targets that long is judged against an unknown directory and denied as unparseable where creations are guarded.

### Known limits

The lane guard is a best-effort detector of the text of one command line, and the git-layer backstop (`arm`) is the enforcement that does not depend on parsing: in a repository the user has armed it vetoes a branch created without a claim whatever tool ran the git binary, within the backstop limits of `references/lane-split.md` section 12. The hooks do not read the classes below; for each, keep the repositories where lanes live armed, run the commands that matter through a script you have reviewed, and stay on the lane discipline of the skill (plan before creating, never work around a denial) unless the class names another remedy. Section 12 gives every class with its examples.

- **Aliases from places the hook does not read.** `--config-env`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `-c include.path`, an alias defined on the same line, the aliases of another repository or of a session outside any repository, `-c alias.*` in another case or shadowing a built-in, chains over three aliases and git spelled `git.exe`, `Git` or as a variable are not read; keep the repository the line reaches armed.
- **Command text from configuration or environment.** `core.fsmonitor`, `core.editor`, `sequence.editor`, `diff.external`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `GIT_EXTERNAL_DIFF` and a `rebase --exec` or `bisect run` text with a dynamic program are not inspected; keep the repository armed.
- **Wrappers and program spellings outside the walker's lists.** `ionice`, `flock`, `taskset`, `coproc` and similar wrappers, a path-qualified `env`, `nohup`, `xargs` or `sudo`, ANSI-C quoting (`$'g\x69t'`), a backslash-newline inside the program word, an empty expansion or a substitution as the program, a program held in a variable or computed, and shells such as `fish` and `tcsh` hide the program; run what matters through a reviewed script and keep the repository armed.
- **Escapes in git words in a tool whose shell is not known.** In a tool whose shell is unknown, a backslash inside a git option word (`-\C`, `--git\-dir=`), a sub-subcommand (`worktree a\dd`) or the ref of `update-ref` is compared as written; keep the repository armed.
- **Text fed to a shell, and scripts.** A creation inside a process substitution, quoted text that names no git fed to a shell (`printf '. ../mk\n' | sh`), a script run directly without a `.sh`, `.bash` or `.ps1` name (`./mk`) and a script another command feeds (`cat ../mk | bash`) are not read; read the script first and keep the repository armed.
- **A directory an earlier command of the line creates.** A `cd` into a directory that `mkdir` creates earlier on the line is followed only in a `&&` chain (`mkdir L/nd; cd L/nd; git switch -c x`); create the directory in a call of its own or chain with `&&`, and keep the repository armed.
- **Pushes and fetches without a readable destination.** `fetch --refmap` and `-c remote.<name>.fetch`, a push into another local repository without a colon refspec (`git push ../R newb`, `--all`, `--mirror`, `HEAD`) and a push whose repository a bundled option value displaces (`-fo x`) are not read; arm the receiving repository too.
- **The symbolic-ref alias two-step.** A symbolic ref outside `refs/heads/` that points into it, then written through `git update-ref`, creates the branch unseen; keep the repository armed.
- **Nested substitution.** A substituted text with another group inside it (`$(git switch -c x $(git rev-parse HEAD))`, `(git switch -c x (git rev-parse HEAD))`) is not read; keep the repository armed.
- **PowerShell tokenising.** A `\"` or doubled backtick before a quote in a double-quoted string, a trailing backslash that joins the next line, a here-string with an apostrophe and a block comment `<# .. #>` are tokenised approximately, so the creation after them can go unjudged and a command-shaped line inside them is denied; keep the repository armed.
- **PowerShell code from strings.** PowerShell code built from a string and run through a script block (`[scriptblock]::Create`) and a program called by a dot (`. git switch -c x`) are not read; keep the repository armed.
- **The switches of `cmd` and its `start`.** `cmd` switches other than a lone `/c` or `/k` (`/r`, `/d/c`, `/cgit`) and `cmd /c start` are not read; keep the repository armed.
- **`Start-Process` of shells and splatting.** A shell that `Start-Process` starts, a call through splatting and an `-ArgumentList` cut at commas and read with shell quoting are not read as written; keep the repository armed.
- **Options of child shells.** `pwsh -WorkingDirectory`, a `powershell -File` script behind four option values and `env -S` with bundled options (`-vS`) or the `\_` separator are not read; keep the repository armed.
- **The tamper filter.** The tamper filter does not follow `Start-Process` lists, `cmd /r`, `env -S`, `iex` and `ScriptBlock::Create`, so the git layer itself can be removed; run `doctor` to see that it is still installed and re-run `arm` when it is not.
- **MCP tools without a string `command`.** MCP command tools whose command is a list or sits under another key (`cmd`, `script`, `argv`, `commandLine`, `input`) are allowed without parsing; keep the repository armed.
- **Over-denials by text or name.** A prompt that mentions `isolation: worktree`, quoted git text beside a here-string, an MCP tool named `get_branch`, the help forms of `gh pr checkout`, `git config magos.<key>` as a read and git options that print and exit are denied although they create nothing; run them in your own terminal.
- **Unreadable `update-ref --stdin`.** An `update-ref --stdin` fed from a file, another command or text with an expansion is denied as dynamic even when it only deletes; the hook reads it only when a here-document, a here-string or a piped `echo` or `printf` feeds it.
- **Launcher input cost.** The sh half of the launcher costs quadratic time for a payload of tens of thousands of raw lines; no agent can cause it, and a host that pretty-prints its payload should send one line.

1. Upgrade the plugin on each host (`references/installation.md`, "升级"). Restart every running Claude Code session: a session started before the update keeps running the previous guard. A Hermes install pinned with `--ref` moves its pin with `hermes plugins install UlyssesLeoLee/MAGOS --ref <40-character SHA of v1.0.3> --force --enable`; `hermes plugins update` and a reinstall without `--ref` keep the old commit.
2. Refresh the guard copy: run `doctor` from the new version (with `--home <dir>` for a copy installed with `install --home <dir>`) and, in your own terminal, the `install --host <host>` commands it prints. ### Security

- **Repository redirects.** A creation redirected into another repository with `git --git-dir`, `GIT_DIR` or `GIT_COMMON_DIR` (prefix, `env`, `export`, PowerShell `$env:`, cmd `set`) was allowed without a manifest: the hook judged the session's repository, or none when the session was outside any repository, so a claim there or a session repository with no other lane let an unplanned lane be created in the other repository. Each creation is judged in the repository it acts on, with that repository's mode, engagement and claims; under `GIT_COMMON_DIR`, which makes Git use two repositories at once, it is judged in both; a redirect the hook cannot resolve is denied in every mode, and so is a creation after a `GIT_DIR` or `GIT_COMMON_DIR` change the hook does not follow (`read`, `printf -v`, `+=`, `builtin export`, `Set-Content Env:`). `--work-tree` and `GIT_WORK_TREE` alone leave the judged repository unchanged.
- **Directory changes the shell may not make.** A `cd`, `pushd`, `Set-Location` or `GIT_DIR` change that the shell might never make before the creation moved the hook's judgement into another repository: one after `&&` or `||` followed by `;` (`false && cd other; git branch x`), inside `if`, `case` or a loop, in a function body or a PowerShell script block, in a background job (`&`), in a subshell `( )`, a command substitution `$( )`, a pipeline, `eval`, `source`, a PowerShell `( )`, or written as `env cd` (which changes nothing). The creation is judged in every directory the shell may be in, and the stricter verdict applies; in bash a subshell's change is known not to reach the commands after it. `cd dir && git switch -c x` and `cd dir; git switch -c x` are still judged in `dir` only.
- **Directories handed to wrappers.** `env -C <dir>` (`--chdir`) and `sudo -D <dir>` (`--chdir`) run git in `<dir>`, but the hook judged the directory the shell was in. They are judged like `git -C <dir>`. A session directory written with `~` (`~/repo`, `~user/repo`) is expanded, and a relative tool directory is joined to the payload's directory.
- **`cd` to a missing directory.** `cd` or `Set-Location` to a directory that does not exist, followed by `;` or a newline, let the following branch or worktree creation through, although the shell runs it in the prior directory. For `cd`, `pushd`, `chdir`, `Set-Location` and `sl`, the creation is judged in that prior directory and denied as unparseable when it is guarded, on every platform; the same holds for a `cd` the shell refuses (`cd /d dir` in bash, `cd dir extra`), while cmd's `cd /d dir` is followed into `dir`.
- **Shells and wrappers that hid a creation.** Text piped into a shell was read only when the shell stood right after the pipe, so `| FOO=1 sh`, `| env bash`, `| sudo -E sh`, `| command sh` and `| doas sh` let a creation through; `doas git branch x`, PowerShell `$out = git switch -c x`, `(git switch -c x)` and `@(git switch -c x)`, `env -S 'git switch -c x'`, and the commands `git rebase --exec` and `git bisect run` run were not recognised. All of these are read as the creation they run.
- **Escaped words.** In text a POSIX shell runs, a backslash escape hid a creation or a user-only command (`git swi\tch -c feat\ure`, `g\it`, `bash -\c`), and a cmd caret (`feat^ure`) did the same in cmd text. Words are read the way the shell that runs them reads them; in a shell the hook cannot name, a backslash in a git subcommand or branch name makes the creation dynamic. A bash backslash-newline joins the words around it (`main\<newline>2` is `main2`), and a `#` comment ends at the line's end, so a quote in a comment (`# Let's ...`) hides none of the following commands.
- **Git command spellings.** A branch name attached to its option (`git switch -cNAME`, `git checkout -qbNAME`, `git worktree add -bNAME <dir>`, `--orphan=NAME`), a global option whose value hid the subcommand (`--attr-source <v>`, `--config-env`, `--namespace`, `--exec-path`), a rename or copy written with bundled or abbreviated options (`git branch -mf`, `-qm`, `--mo`, `--cop`), the creating options of `git switch` and `git checkout` abbreviated to two letters (`--cr`, `--or`), a branch name after `git branch --sort <key>` or `--format <format>`, a push or fetch whose option value stood before the repository (`git push --exec <v> . HEAD:refs/heads/x`, `-o <v>`), a refspec that creates branches by a glob (`refs/heads/x-*`), a `git push` into a local repository (`git push . HEAD:refs/heads/x`, `git push ../other HEAD:x`), and an alias on a line that also held a recognised command created a branch without a manifest. Each is recognised; a push into a local repository is judged in that repository.
- **Unhooked shell tools in Claude Code.** The `Monitor` tool and MCP tools that run commands (`run_in_terminal`, `terminal`, `shell`, `exec_command`, `execute_command`, `start_process`, and names holding `command`, `exec`, `execute`, `process`, `bash`, `powershell` or `cmd`) were not inspected. They are hooked, the Claude matcher is generated from the guard's tool list, and the `command` string of every hooked tool and every MCP tool is read as a command line in addition to the judgement the tool's name calls for. `tool_input.cwd` is read as the session directory.
- **Payloads the hook could not decode.** A payload whose decoding raised (deep nesting gives `RecursionError` or `MemoryError`) was allowed. It is denied when its bytes hold a lane word (`git`, `worktree`, `isolation`, `EnterWorktree`, `magos` and the like), and an internal error on a call recognised as a lane creation or a protected command denies that call.
- **Programs in the working directory (Windows).** The launcher and the guard could run a `py`, `python` or `git` placed in the hook's working directory. Both set `NoDefaultCurrentDirectoryInExePath=1` before starting any program, and the launcher's cmd half finds its interpreter on PATH only.
- **User-only commands.** `override`, `arm`, `disarm` and `install` passed the host hook when a global option was written as `--repo=.`, `--lang=en` or abbreviated (`--rep .`), when `--` stood before the subcommand, when they were run through the launcher `run-guard.cmd`, and when a wrapper started them in a new console (`start`, `cmd /c start`, `Start-Process`). They are recognised in all of these forms, options are never abbreviated, the launcher runs only the `hook` subcommand (exit 2 for any other), and `install` needs a real console like `arm` (exit 17).
- **AUTO engagement.** When the check for other lanes failed (for example on the time budget), an auto-named worktree (agent isolation, `gh pr checkout`) was allowed, and more than 120 unmerged local branches made AUTO allow branch-only and auto-named creations without a warning. A snapshot that hides lanes counts as another lane; when the check fails, an auto-named creation is denied if an open claim, another local branch or a second worktree exists, a branch-only creation is judged when the repository holds a claim, and every undecided call writes a warning on stderr.
- **Overrides.** The host hook honoured an override record without consuming it. Only `plan` reads override records; after the user's override, a re-plan registers it in the claim, and the hook honours only the claim.
- **Claim store.** `release` with another spelling of the branch (`./x`, a different case) skipped the refusal for unmerged work and could delete a file outside the claim store; branch names that alias on Windows (`foo./bar` and `foo/bar`, names ending in `.claim`) overwrote another lane's claim; a newline in `--worktree` or `user.name` added lines to a claim file; two planners could register clashing names at once; and on Linux `release` with a spelling that holds `..`, `.`, an empty segment or a backslash (`zz/../FEAT`) found no claim. `release` reads the branch as a ref spelling (a backslash as `/`, empty and `.` segments dropped, `..` resolved), resolves the stored claim and deletes only its file inside the store; aliasing names are refused (exit 12); control characters are refused or replaced and claim keys are whitelisted; the name check runs again under the claim lock.
- **Tamper filter.** Writes aimed at the claim store, the guard home or the Hermes plugin directory by their absolute path are denied in armed or claimed repositories, as `.git/...` spellings are; `unlink`, `truncate`, `shred`, `ln`, `rmdir`, `rd`, `mklink`, `find -delete`, `Rename-Item`, `Move-Item`, cmd's `move` and `copy`, PowerShell's `cpi`, `sc`, `ac`, `ni` and `clc` and their aliases count as writers, also inside the text of a child shell (`cmd /c`, `bash -c`, `pwsh -Command`); a word escaped with a backslash, a backtick or a caret matches like its plain spelling. A copy is tested on every destination spelling (`-Destination:<path>`, operands before an option value such as `-ErrorAction Stop`); copying from the guard home is allowed.
- **Launcher on Windows.** An interpreter that is a `.bat` or `.cmd` shim did not return to the launcher, so its exit code was lost; a guard home whose path held `&`, `(`, `)`, `^`, `%`, `;`, `,` or `=` broke the generated entries or ran text from the path as a command; a guard home with an apostrophe broke the Codex entry. The launcher runs its interpreter through `call`, `install` refuses such a guard home on Windows (exit 2) and quotes the launcher path for each shell, and the launcher passes the guard's stderr to the host.
- **Chained git hooks.** `arm` keeps a repository's own `reference-transaction` hook as `reference-transaction.magos-prev` and runs it from the backstop. On POSIX a previous hook without the executable bit, which git itself never runs, failed with exit 126 in the `prepared` phase and so aborted every ref update in the armed repository. The backstop runs the previous hook only when it is executable, as git does.
- **Write adapters in Claude Code.** `git-integrate`, `git-cleanup`, `git-converge` and `git-sweep` set `disable-model-invocation: true`: only the user's slash command runs them.
