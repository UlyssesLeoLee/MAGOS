# GitPlan

Command adapter for the canonical `/GitPlan` command of the MAGOS (Multi-Agent Git Orchestrator) package. It plans, before any sub-agent starts, how one task is divided into lanes that are merged back as one whole, and later converges them. Use it only when the user explicitly invokes `/git-plan` in Hermes or `$git-plan` in Codex.

## Usage

- Hermes: `/git-plan <set> (--into <branch> | --status | --amend | --converge | --release) [--apply] [--create] [--expect-revision <n>] [--include-active] [--land] [--lang <language>] [--help]`
- Codex: `$git-plan <set> (--into <branch> | --status | --amend | --converge | --release) [--apply] [--create] [--expect-revision <n>] [--include-active] [--land] [--lang <language>] [--help]`

Forms (the selecting option `--into`, `--status`, `--amend`, `--converge` or `--release` chooses the form; two selecting options together, or an option the form does not list, is a usage error; `--lang <language>` and `--help` go with every form; written for Hermes, Codex uses `$git-plan` in place of `/git-plan`):

- `/git-plan <set> --into <branch>`: preview the plan: investigate Git and the code, write the requirements of the task, divide it into lanes with exclusive file ownership that are named after the topic of their change, prove it and print the Requirements table and the Lanes table (read-only).
- `/git-plan <set> --into <branch> --apply`: register the plan the preview showed and print both tables from the record.
- `/git-plan <set> --into <branch> --apply --create`: register it, also create the lane branches and worktrees, and print both tables from the record.
- `/git-plan <set> --status`: both tables with the state and the head of every lane (once a lane is integrated, also what it changed: the Changes column, the Result column and the Changes summary) and what remains (read-only).
- `/git-plan <set> --amend --expect-revision <n>`: preview the re-plan of a registered set with both tables (read-only).
- `/git-plan <set> --amend --expect-revision <n> --apply [--create]`: register the amended plan and print both tables from the record.
- `/git-plan <set> --converge [--include-active]`: preview the convergence: both tables with the state of every lane, the merge plan and what remains (read-only).
- `/git-plan <set> --converge --apply [--include-active] [--land] [--expect-revision <n>]`: merge the lanes into the integration branch and print the original tables supplemented with the changes of every lane (Changes, Result, the Changes summary and its Total line); `--land` also fast-forwards `<branch>`.
- `/git-plan <set> --release`: print the supplemented tables, then retire the set after its lanes are integrated.

Arguments and options:

- `<set>`: Required (except with `--help`). Name of the plan: `[a-z0-9][a-z0-9-]{0,23}`, matched case-sensitively, and not a Windows device name (`con`, `nul`, `com1`, ...). It names the set record and the claims of its lanes.
- `--into <branch>`: Required to plan. Local branch the plan is made against and that `--land` later fast-forwards. Matched exactly (case-sensitive); it must not be `main`. The other forms read it from the set record.
- `--apply`: With `--into`: register the plan the preview showed (the lane claims, the claim of the integration branch and the set record, written only through `magos_guard.py`). With `--amend`: register the amended plan. With `--converge`: merge the lanes into the integration branch. Without it, only a preview is shown.
- `--create`: With `--apply` of a plan or an amendment: also create the branches and worktrees of the registered lanes that do not exist yet. Without it the apply prints the `git worktree add` lines for you to run.
- `--status`: Read-only checklist: the sheet with the state of every lane and what remains.
- `--amend`: Re-plan a registered set. Needs `--expect-revision`.
- `--expect-revision <n>`: The record revision (a positive integer) the amendment, or with `--converge --apply` the previewed convergence, was made against; a record at another revision stops the command.
- `--converge`: Preview the merge of the lanes, in dependency order, into one integration branch `agent/<set>/integration`; with `--apply`, run it: each ready lane's recorded head is merged with `git merge --no-ff` and recorded `integrated`, and the repository checks run on the result. A conflict aborts that merge and stops the run; it is never resolved with ours or theirs.
- `--include-active`: With `--converge`: treat a lane in state `active` that holds changes of its own against the current target as ready at its current tip, which the preview shows as its Head. In an apply this is your acceptance of those tips; a tip that moved since the preview stops the apply with a new preview.
- `--land`: With `--converge --apply`: after the merges and the checks, fast-forward `<branch>` to the integration branch with `git merge --ff-only`, only when `<branch>` still sits where the integration branch was cut from; otherwise it stops and says to rerun. It is refused, before any merge, while a lane is not ready or integrated (run without `--land` first).
- `--release`: Retire the set once its lanes are integrated: remove its claims and its record. The lane branches, their worktrees and the integration branch are not touched.
- `--lang <language>`: Language of the reply, as a name or code (for example `English`, `ja`); Chinese when absent. Command names, options, branch names, paths, SHAs, and status codes stay untranslated.
- `--help`: Show this inline usage and argument description, then stop without inspecting or changing the repository.
- Default: Investigate Git and the code, then print the plan preview: the Requirements table (each requirement of the task with the lanes that serve it and their planned outcomes), the Lanes table (branch, worktree, owned paths, dependencies, acceptance), the merge line, the shared files and the risks, the topic each lane id names, the proof that the lane manifests are pairwise disjoint (`magos_guard.py set-plan --dry-run`) and a readiness verdict (`READY` or `BLOCKED`) with the next command and the remedy for every failed gate; nothing is registered, created or merged, nothing is fetched, and the only write is a scratch spec file outside every worktree.

The plan divides one task into lanes (sub-agent worktrees) that own disjoint files and are merged back as one whole, and it lists the requirements of the task, the lanes and the outcomes in two tables. The preview investigates Git (branches, worktrees, open claims, the target tip, remote freshness as it is known locally) and the code (layout, entry points, test and build commands, shared files, hot spots, coupling), writes the requirements of the task as `R1`, `R2`, ... and prints a concise checklist, the sheet, of at most 8192 characters: the Requirements table (`Req`, `Requirement`, `Lane(s)`, `Planned outcome`: one row per requirement) and the Lanes table (`Lane`, `Branch`, `Worktree`, `Owns`, `Needs`, `Acceptance`: one row per lane), one merge line, the shared files with their owner lane and at most five risks. Every requirement is served by at least one lane, and every lane serves at least one requirement and states the outcome it delivers. Names show the topic of the change: a lane id is a topic slug of one to three words (`claim-store`, `sweep-docs`; `[a-z0-9][a-z0-9-]{0,23}`), its branch is exactly `agent/<set>/<id>` and the name of its worktree directory ends with `-<set>-<id>`, so `git branch` and `git worktree list` read as a list of topics; the guard refuses an ordinal or generic id such as `l1`, `lane-2` or `task3` (exit 24). The tables are rendered from the spec the guard proved (a preview) or from the record the guard stores (afterwards), never from memory. `magos_guard.py set-plan --dry-run` proves that the lane manifests are pairwise disjoint, that every shared file lies inside exactly one lane, that the dependencies form a DAG and that every requirement is served; the guard must be version 1.0.4 or later, otherwise the command stops and says to refresh it. The plan is registered with an optimistic lock: nobody holds a lock while the lanes work, the record carries a revision and the target SHA it was planned against (`base`), a stale plan is detected and never overwritten, and the owner of a lane records it `ready` with its head SHA when it finishes. After the lanes finish, `--status` and `--converge` print the tables again from the record with the State and the Head of every lane, followed by Remaining TODO (the lanes still to finish, the merges, the repository checks, the post-merge tasks, the land and the release), so the tables are the TODO reference for the merge. After the merge the original list is supplemented with the changes: when a lane is recorded `integrated` the guard stores a summary of what it changed (commits, subjects, files, insertions, deletions, paths), and the converge apply report, `--status` and `--release` print the same tables with a Changes column on the lanes table and a Result column on the requirements table, then the Changes summary (one line per lane) and a Total line; no row or column of the plan is removed. Semantic coupling across files is not detected by the guard: coupled files go into the same lane. While the set is open, its lane claims make `/GitCleanup`, `/GitConverge` and `/GitSweep` report those branches as `BLOCKED_ACTIVE_OWNER`; `--release` lifts that. The command never pushes, never forces, never deletes a branch or a worktree, never touches `main`, never uses `override`, never rebases or squashes, and never resolves a conflict with ours or theirs: a conflict aborts the merge and stops the run, with the completed merges kept on the integration branch only.

Examples: `/git-plan sweep-readiness --into develop`, `$git-plan sweep-readiness --into develop --apply --create`, `$git-plan sweep-readiness --status`, `$git-plan sweep-readiness --converge --apply --land`, `$git-plan --help`.

## Execution

Execute the canonical `/GitPlan` command only when the user explicitly invoked this command skill. Preview by default; write only when the explicit command includes `--apply` (or is `--release`) and every gate still passes. A preview investigates Git and the code read-only, proves the partition with `magos_guard.py set-plan --dry-run`, fetches nothing and uses no network, and writes nothing but a scratch spec file outside every worktree. With `--apply` of a plan or an amendment, register exactly the spec of the latest preview of the same set and target in this conversation (make a new preview and stop when there is none, when the user asked for a change since it, when its `base` differs from the live target tip, or, for an amendment, when it was built from another record revision than the current one); with `--create`, also create only the registered lane branches and worktrees, at their registered paths, from the recorded `base`. With `--converge --apply`, record the plan first (lane order, recorded heads, target tip, revision) and include it in the final report, create the integration branch `agent/<set>/integration` from the current target tip in the invoking worktree when it is absent (that worktree must be on the target with no tracked change and no operation in progress; its untracked files, such as files the repository checks wrote, do not block and are listed in the report), merge each ready lane's recorded head into it with `git merge --no-ff`, record each merge through `magos_guard.py set-update`, run the repository checks, and only with `--land` fast-forward `<branch>` once with `git merge --ff-only`. With `--release`, print the final supplemented tables first, then remove the claims and the record through `magos_guard.py set-release`; no branch, worktree or integration branch is touched. Stop on a conflict: run `git merge --abort`, never resolve it with ours or theirs, and keep the completed merges on the integration branch only. Write the claim store and the set record only through `magos_guard.py set-plan`, `set-update` and `set-release`. Never push, force-push, fetch or use the network; never move, merge into or delete `main`, and never take `main` as the target; never delete a branch or a worktree and never run `git worktree prune`; never use `override`, `arm`, `disarm` or `install`, never run the guard's plain `plan` or `release` on a claim of a set and never edit `.git/magos`; never rebase, squash, cherry-pick or reset; never pass `--no-verify`, `-X ours`, `-X theirs` or `--allow-unrelated-histories` to a merge; never write inside a lane worktree. Merge nothing but a recorded lane head into the integration branch (and, with `--land`, the integration branch into `<branch>` by one `--ff-only` merge); create no branch or worktree other than a registered lane (at its registered path, from the recorded `base`) and the integration branch; never shrink, amend or release the claim of a lane to make a conflict disappear. Git and guard commands run as argument lists, never as shell strings. Show the plan as the contract says: the Requirements table and the Lanes table (in the supplemented form once a lane is integrated), rendered from the guard's dry-run result or from its record, never from memory; name every lane id, branch and worktree after the topic of its change and never by ordinal (`references/commands.md` section 8, **Partition rules**). Ask for a set name if none is provided. Reply in the language selected by `--lang` (Chinese when absent); never translate commands, options, branch names, paths, SHAs, or status codes. Remove `--lang` and its value from the arguments before parsing the rest.
